الخطة الهندسية الكاملة لبناء DevTape بلغة Rust: من النواة وحتى الإصدار 1.0

مخطط تفصيلي يغطي جميع الوظائف النهائية، ومعمارية الـ 8 حزم (Crates)، وميزانية الأداء الصارمة على المعالج والذاكرة والقرص، مع تحليل أعمق 8 معوقات تقنية وحلولها الهندسية الدقيقة قبل كتابة أول سطر كود.

< 2 ms

الحد الأقصى للتأخير المضاف على كتابة الطرفية (PTY Latency Budget) لضمان أن المبرمج لا يشعر بوجود المسجّل إطلاقاً.

الوظائف النهائية الكاملة التي سيصل إليها النظام في الإصدار 1.0

لتحقيق انتشار عالمي واسع، يجب أن يعمل DevTape كطبقة بنية تحتية صامتة تعمل محلياً بالكامل وتخدم كل مبرمج يومياً. ينقسم المنتج النهائي إلى ست ركائز وظيفية متكاملة، كل ركيزة قابلة للتفعيل أو التعطيل بشكل مستقل حتى لا تفرض أي عبء غير مطلوب على الجهاز.

الركيزة 1 · التقاط الطرفية

تسجيل الجلسة والأوامر (PTY)

تشغيل غلاف طرفية شفاف عبر devtape record يدعم zsh وbash وfish وPowerShell. يسجل كل أمر، ووقت بدايته ونهايته، ورمز الخروج (Exit Code)، وتغيير حجم الشاشة (SIGWINCH)، ومخرجات ANSI الملونة بدقة كاملة قابلة لإعادة العرض البصري.

الركيزة 2 · الرجوع بالزمن

لقطات الكود والاستعادة الفورية

أخذ لقطات غير تدميرية لشجرة المشروع عبر git write-tree في فهرس مؤقت منفصل تماماً عن سجل الـ Commits. يتيح تنفيذ devtape rewind -5m أو الرجوع قبل أمر معين، مع دعم استعادة ملف واحد فقط أو مقارنة الفروقات (Diff) بين أي لحظتين في الجلسة.

الركيزة 3 · الخصوصية أولاً

تنظيف الأسرار التلقائي

فحص فوري لكل بايت قبل حفظه عبر محرك هجين يجمع بين مطابقة الأنماط السريعة (مفاتيح AWS، GitHub، OpenAI، JWT، سلاسل الاتصال) وحساب الإنتروبيا (Shannon Entropy) وقراءة أسماء متغيرات .env. يفرض شاشة مراجعة --review قبل أي تصدير خارجي.

الركيزة 4 · الشبكة المحلية

اعتراض حركة الـ API المحلية

وكيل محلي اختياري (--net) يعترض طلبات HTTP/1.1 وHTTP/2 وgRPC على المنافذ المحلية والواجهات الخارجية، ويربط كل طلب واستجابة ووقت استجابة باللحظة الزمنية الدقيقة للأمر الذي أطلقه في الطرفية دون تعديل سطر واحد في كود التطبيق.

الركيزة 5 · وكلاء الذكاء الاصطناعي

تكامل MCP وتتبع الوكلاء

تسجيل كل استدعاء أداة (Tool Call) وتعديل ملف ينفذه وكيل برمجة (مثل Claude Code أو Cursor أو Codex)، مع نقطة استعادة تلقائية قبل كل خطوة وكيل. كما يشغّل خادم MCP محلي يمكّن أي وكيل من الاستعلام عن الخطأ داخل ملف .tape وإصلاحه بدقة.

الركيزة 6 · المشاركة والمنظومة

ملف .tape والواجهة المدمجة وCI

تصدير الجلسة كملف .tape واحد مضغوط بـ Zstd، وفتح واجهة Timeline تفاعلية محلياً عبر devtape view (مدمجة داخل الملف التنفيذي)، بالإضافة إلى عارض WebAssembly يعمل في المتصفح بدون تثبيت، وGitHub Action يرفق تسجيلات الاختبارات الفاشلة تلقائياً في الـ PR.

معمارية Rust Workspace وفصل المسارات الحرجة عن التخزين

أهم قرار معماري في DevTape هو الفصل التام بين المسار الساخن (Hot Path) والمسار البارد (Cold Path). يجب ألا ينتظر المستخدم القرص أو قاعدة البيانات أو محرك التنظيف أثناء الكتابة في الطرفية.

تعمل النواة بنمط الممثلين غير المتزامنين (Async Actor Pipeline): يمرر devtape-pty كل بايت مباشرةً إلى شاشة المستخدم أولاً، ثم يرسل نسخة غير حاجزة عبر قناة ذاكرة محدودة (Bounded Channel) إلى مسار التنظيف والضغط والتخزين المجمّع.

  • devtape-cli: نقطة الدخول باستخدام clap، تدير الأوامر (record، rewind، diff، export، view، mcp، doctor) وإعدادات ملف .devtape.toml.
  • devtape-pty: تغليف الطرفية عبر portable-pty مع دعم كامل للتدفق الثنائي، وحقن خطافات Shell خفيفة (preexec / precmd) لالتقاط حدود كل أمر ورمز خروجه بدقة.
  • devtape-git: مراقب ملفات ذكي عبر notify مع Debounce (كل 300ms أو عند انتهاء كل أمر)، ينفذ git write-tree باستخدام GIT_INDEX_FILE مؤقت حتى لا يمس Staging Area الخاص بالمطور.
  • devtape-scrub: محرك تنقيح متدفق يعتمد على aho-corasick + regex + كاشف Shannon Entropy، ويعمل على النوافذ المتداخلة (Sliding Window) حتى لا يفلت مفتاح مقسّم بين حزمتي PTY.
  • devtape-net: وكيل عكسي/أمامي محلي مبني على tokio وhyper مع توليد شهادة TLS مؤقتة للجلسة فقط عبر rcgen عند تفعيل --net.
  • devtape-core: محرك التخزين بنمط Single-Writer على rusqlite (وضع WAL) مع مخزن كائنات Content-Addressed مفهرس بـ blake3 ومضغوط بـ zstd.
  • devtape-mcp: خادم JSON-RPC عبر stdio يوفّر للوكلاء أدوات مثل tape_get_failures وtape_get_diff وtape_search_logs.
  • devtape-ui: واجهة React/TypeScript خفيفة تُبنى كملفات ساكنة وتُدمج داخل الملف التنفيذي بـ rust-embed وتُخدم عبر axum على 127.0.0.1 فقط.

تحليل الأداء وميزانية الموارد لكل وحدة في النظام

يفشل أي مسجّل تطوير محلي فوراً إذا رفع حرارة الجهاز أو أبطأ بناء المشروع أو استهلك غيغابايت من القرص. لذلك نضع ميزانية موارد صارمة لكل وحدة تُقاس تلقائياً في الـ CI: إجمالي الاستهلاك النشط يجب أن يبقى تحت 2% من المعالج، وأقل من 45 MB من الذاكرة، وأقل من 5 MB لكل ساعة عمل على القرص بعد الضغط.

أعمق 8 معوقات تقنية متوقعة وحلولها الهندسية الدقيقة

نجاح مشروع مفتوح المصدر بهذا الطموح لا يتوقف على الفكرة بل على معالجة الحالات الحدية التي تُحبط المطورين في الأسبوع الأول. الجدول التالي يوثق كل عائق هندسي حقيقي، وتأثيره المباشر على الأداء أو الأمان، والحل الدقيق بلغة Rust.

المعوق التقني الأثر على الأداء أو التجربة الحل الهندسي المعتمد في Rust
1. تضخم المستودعات الضخمة (Monorepos > 50K ملف) بطء أخذ لقطات Git وتضخم القرص عند حفظ مجلدات مثل target/ أو node_modules/. احترام .gitignore تلقائياً + استخدام GIT_INDEX_FILE مؤقت لتجنب تعديل فهرس المطور + تجزئة الملفات المعدّلة فقط بـ blake3 وإلغاء التكرار (Deduplication) + حد أقصى افتراضي لحجم الملف المفرد (10 MB).
2. فيضان مخرجات الطرفية (PTY Output Flood) طباعة ملايين الأسطر (مثل cargo test --nocapture أو cat لملف ضخم) قد تجمّد الطرفية أو تملأ الذاكرة. استخدام Bounded Channel (سعة 16 MB). إذا امتلأت القناة لا تتوقف الطرفية أبداً؛ بل يتم إسقاط الحزم الزائدة وتسجيل علامة [devtape: 4.2 MB output truncated] مع الحفاظ على أول 32 KB وآخر 32 KB من الأمر.
3. انقسام الأسرار بين حزم التدفق + الإيجابيات الكاذبة قد يصل مفتاح API مقسّماً على حزمتي TCP/PTY فيفلت من التنقيح، أو يُخفى Hash عادي بالخطأ. تطبيق نافذة متداخلة (Overlap Window بطول 256 بايت) بين الحزم المتتالية، وقصر فحص Shannon Entropy على السطور التي تحتوي كلمات سياقية (key، token، secret، auth)، مع إجبار المطور على معاينة devtape export --review.
4. فروقات أنظمة التشغيل (macOS / Linux / Windows) اختلاف آلية PTY وإشارات تغيير حجم الشاشة وأوامر الـ Shell بين Unix وWindows ConPTY. الاعتماد على portable-pty وبناء طبقة تجريد صغيرة (OsAdapter) لإشارات النافذة ومسارات الملفات، مع تشغيل اختبارات تكامل إلزامية على الأنظمة الثلاثة عبر GitHub Actions في كل PR.
5. احتكاك شهادات HTTPS في الوكيل المحلي المطورون يرفضون أي أداة تطلب صلاحيات Root لتثبيت شهادة CA في النظام العام. توليد شهادة محلية مؤقتة داخل مجلد المستخدم عبر rcgen وحقن متغيرات SSL_CERT_FILE وNODE_EXTRA_CA_CERTS وREQUESTS_CA_BUNDLE داخل جلسة الـ PTY الفرعية فقط—صفر تعديل على النظام العام.
6. تعارض الكتابة في SQLite (Database Locked) وجود 4 خيوط تكتب في وقت واحد (PTY، Git، Net، MCP) يسبب أخطاء قفل أو بطء I/O. تفعيل وضع PRAGMA journal_mode=WAL وsynchronous=NORMAL، وحصر كل عمليات الكتابة في خيط واحد (Single-Writer Actor) يجمع الأحداث ويكتبها في Batch Transaction كل 500ms.
7. مخاطرة فقدان كود غير محفوظ عند التراجع (Rewind) قد ينفّذ المطور devtape rewind بالخطأ ويفقد تعديلات مهمة كتبها للتو. أخذ لقطة أمان إجبارية (auto-backup snapshot) قبل تنفيذ أي عملية استعادة، وإتاحة أمر devtape undo-rewind لإلغاء التراجع فوراً، مع تشغيل ملفات .tape الخارجية بوضع القراءة فقط (Read-Only).
8. تضخم حجم الملف التنفيذي وبطء التثبيت دمج واجهة ويب ومكتبات ضغط وتشفير قد يرفع حجم الملف فوق 60 MB مما يبطئ التحميل. ضغط أصول الواجهة بـ Brotli قبل دمجها بـ rust-embed، واستخدام إعدادات lto = "thin" وstrip = true وcodegen-units = 1 لإبقاء حجم الملف التنفيذي النهائي أقل من 15 MB.

تصميم صيغة ملف .tape المفتوحة ونموذج الأمان

جعل صيغة .tape مواصفة مفتوحة وموثّقة هو ما يحوّل DevTape من مجرد أداة إلى معيار صناعي (Standard Format) تتبناه أدوات الـ CI والـ IDEs ووكلاء الذكاء الاصطناعي.

  • ترويسة تعريفية ثابتة (Magic Header): تبدأ بـ DTAP01 مع رقم إصدار الصيغة لضمان التوافق الخلفي (Backward Compatibility) مدى الحياة.
  • بيان الجلسة (manifest.json): يحتوي نظام التشغيل، نوع الـ Shell، رقم فرع Git الأولي، مدة التسجيل، وقائمة الإضافات المفعّلة—دون أي مسار مطلق يكشف اسم المستخدم (يُستبدل /Users/name بـ ~ تلقائياً).
  • سجل الأحداث الموحّد (SQLite Compressed): جدول events واحد يربط كل حدث برقم تسلسلي وطابع زمني بدقة الميكروثانية ونوعه (pty_in، pty_out، cmd_exit، git_tree، http_tx، agent_tool).
  • مخزن الكائنات (Content-Addressed Blobs): تخزين فروقات الملفات ومخرجات الشبكة مفهرسة بـ blake3 ومضغوطة بـ Zstd؛ الملفات المتكررة لا تُخزّن مرتين أبداً.
  • فصل خريطة التنظيف (Local-Only Redaction Map): تُحفظ خريطة فك الإخفاء في مجلد محلي مشفر على جهازك فقط ولا تدخل إطلاقاً داخل ملف .tape المصدّر، مما يستحيل معه استرجاع أي سر من ملف تمت مشاركته.
«قاعدة الأمان الأولى في DevTape: لا يُفترض أن يثق المطور بوعودك—بل يجب أن يستطيع فحص كل بايت في ملف .tape قبل مشاركته بنقرة واحدة.»

خارطة التنفيذ الشاملة على 4 مراحل ومعايير القبول القياسية

تنتقل الخطة من نواة CLI صلبة خلال الأسابيع الأربعة الأولى، إلى نسخة Alpha عامة في الأسبوع السابع لجمع ملاحظات المطورين مبكراً، ثم منظومة الوكلاء والـ CI وصولاً لإطلاق الإصدار 1.0 في الأسبوع السادس عشر.

بروتوكول الجودة وقياس الأداء الإلزامي قبل كل إصدار

لكي يثق عشرات الآلاف من المطورين بتشغيل DevTape داخل بيئة عملهم اليومية، يجب أن تكون كل مساهمة (Pull Request) محكومة ببوابات جودة آلية لا تسمح بتراجع الأداء أو تسرب البيانات.
